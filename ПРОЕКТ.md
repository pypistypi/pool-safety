всё: что за система, где что лежит, как устроен код, что уже сделано, что

Дата последнего обновления: **7 сентября 2026**. Версия **1.3.0** — выпущена:

## 1. Что это за система

Программа видеонаблюдения за зоной бассейна для **гостиницы в Красной Поляне
(Сочи)**. Помещение **арендованное** — капитальные работы в чаше невозможны.
Заказчик — владелец, разработка полностью делегирована исполнителю.

### Несущий принцип, от которого нельзя отступать

Система **не ставит диагноз «человек тонет»**. Надёжной модели распознавания
утопления не существует: настоящее утопление тихое (на крик и размахивание не
остаётся дыхания), обучающих записей нет ни у кого, вода мешает камере бликами
и преломлением.

Она делает выполнимое: **не даёт человеку остаться незамеченным**. Перестал
двигаться, лежит, упал, завис в воде — оператора зовут посмотреть. Спасает не
распознавание, а то, что спасатель взглянул на десятой секунде, а не на
девяностой.

Это не осторожность в формулировках, а юридическая позиция: система,
заявленная как «распознаёт утопление», при пропуске становится причиной иска.

### Два вида сигналов — разделены в коде, в интерфейсе и по цвету

| | Сигнал 1 — присутствие | Сигнал 2 — тревога |
|---|---|---|
| Когда | в зону вошёл 1+ человек | найдено опасное положение |
| Цвет | зелёный | красный (и только здесь) |
| Эскалация | **никогда** | да, до квитирования |

Между ними есть промежуточный уровень «внимание» (оранжевый).

### Жёсткие ограничения

- **Лица не распознаются.** Только положение тела. Персональных данных не
  возникает (152-ФЗ).
- **Всё локально.** Ни одного обращения в интернет, никаких облаков.
- **Изображение не сохраняется.** В журнал идут время, номер панели и текст.
- **Лицензии только permissive.** Ultralytics (YOLOv5/v8) — AGPL-3.0, для
  гостиницы неприемлемо. Используются YOLOX и RTMPose (Apache 2.0), Qt (LGPL),
  ONNX Runtime (MIT).

## 3. Как собрать и запустить

```powershell
# программа: сборка → проверки → поставка → архив → установщик
powershell -ExecutionPolicy Bypass -File deploy\build_release.ps1

# приложение для телефона
powershell -ExecutionPolicy Bypass -File ..\pool_safety_android\deploy\build_apk.ps1 release
```

Итог выпуска 1.2.0:

| Что | Где | Размер |
|---|---|---|
| Установщик для компьютера | `dist\Установщик\Наблюдение за бассейном 1.2.1.exe` | 126 МБ |
| Архив без установки | `dist\PoolSafety-1.2.1.zip` | 134 МБ |
| Приложение для телефона | `..\pool_safety_android\dist\PoolSafetyWatch-release.apk` | 7 МБ |

Нужны Qt 6.11.1 (MinGW 64) в `C:\Qt`, Inno Setup 6 (стоит в
`%LOCALAPPDATA%\Programs\Inno Setup 6`), JDK 17 (для будущего Android).

Вручную:

```powershell
$env:PATH = "C:\Qt\Tools\CMake_64\bin;C:\Qt\Tools\Ninja;C:\Qt\Tools\mingw1310_64\bin;C:\Qt\6.11.1\mingw_64\bin;$env:PATH"
cmake -S . -B <каталог_сборки> -G Ninja -DCMAKE_BUILD_TYPE=Release -DCMAKE_PREFIX_PATH=C:/Qt/6.11.1/mingw_64
cmake --build <каталог_сборки>
<каталог_сборки>\PoolSafetyTests.exe -o результат.txt,txt
```

Запуск с готовой раскладкой источников (удобно при проверках):

```
PoolSafety.exe --panel1 "путь\к\видео.avi" --panel2 camera:Logitech
```

### ГРАБЛИ СБОРКИ — прочитать до первой сборки

1. **Каталог сборки не должен содержать кириллицу.** `moc` из состава Qt не
   может создать в таком пути свои файлы: «Cannot create moc_*.cpp. Error: No
   such file or directory». Путь проекта содержит «ИИ наблюдение», поэтому
   `build_release.ps1` собирает во временной папке `%TEMP%\PoolSafetyBuild`.
   Сама программа кириллические пути переносит спокойно.
2. **`windres` разваливает пути включения по пробелу.** Поэтому ресурс со
   значком вынесен в отдельную цель `PoolSafetyResources` без
   `target_include_directories`. Плюс нужен ключ `-c 65001`.
3. **Скрипты `.ps1` обязаны быть в UTF-8 с BOM.** Windows PowerShell 5.1 без
   BOM читает их в кодировке системы, и русские строки ломаются до запуска.
4. **Bash-heredoc в этой среде ненадёжен** на содержимом с кавычками и
   кириллицей («unexpected EOF»). Патчи писать файлом через Write, затем
   запускать `python файл.py`.
5. **Тесты пишут в консоль только с** `-o файл,txt` — вывод в этой оболочке
   иначе теряется.

## 5. Решения, которые нельзя «упрощать» обратно

Каждое куплено конкретной проблемой.

1. **Свой `VideoView`, а не `QVideoWidget`.** Штатный выводит картинку в
   отдельное системное окно, поверх которого Windows не рисует дочерние
   виджеты. А поверх видео нужны подписи, скелеты и рамка тревоги.
2. **`SourceHub` — один источник на всех.** Камеру Windows дважды не отдаёт.
3. **Интерфейс остаётся в главном потоке.** Заказчик просил «интерфейс в
   отдельном потоке» — в Qt это невозможно. Требование выполнено иначе: в
   главном потоке нет ни одной тяжёлой операции.
4. **Одна ячейка кадра на панель**, новый вытесняет необработанный.
5. **Итог разбора едет одной структурой `PanelAnalysis`.** Порознь панель
   успевает перерисоваться между обновлениями, и видно три рамки при счётчике «2».
6. **Сирена звучит непрерывно до «ПРИНЯЛ»**, а не по расписанию.
7. **Крестик сворачивает в трей.** Оператор, закрывший окно «чтобы не мешало»,
   выключил бы вместе с ним распознавание и тревогу.
8. **Видео телефону не передаётся через ПК** — только события. Телефон берёт
   картинку прямо с камеры: иначе поток шёл бы по сети дважды.
9. **Длительности состояний считаются накопительно**, а не по истории.
   История 15 с, а пороги бывают 180 с — по истории они недостижимы.

## 6. Что измерено (не переделывать вслепую)

### Сопровождение людей — главная находка

Все временные пороги считаются по дорожке человека. Если дорожка рвётся,
накопленное время обнуляется, и правило не сработает никогда — при том, что
внешне всё исправно: рамки рисуются, люди считаются.

| Сопоставление | Дорожек создано | Живёт в среднем |
|---|---|---|
| пересечение рамок 0,25 — **было** | 204 | **1,2 с** |
| предсказание по скорости + порог 0,15 | 71 | 3,5 с |
| **+ близость центров** (сейчас) | **22** | **11,3 с** |

В живой программе показатель вырос с 1,2 до **20,5 с**. Он выведен в шапку
окна («сопровождение N с») — если там меньше нескольких секунд, правила
сработать не смогут.

### Модели поиска людей (120 кадров, равные пороги)

| Порог | Модель | Найдено в среднем | Провалов счёта | Время |
|---|---|---|---|---|
| 0,25 | YOLOv5n | 5,30 | 56 % | 47 мс |
| 0,25 | **YOLOX-s** | **5,73** | **35 %** | 150 мс |
| 0,25 | YOLOX-tiny | 5,67 | 40 % | 46 мс |

По умолчанию YOLOX-s при пороге 0,25. Кадр **вписывается** с сохранением
пропорций (letterbox), а не растягивается в квадрат.

### Нагрузка (8 логических ядер)

| Режим | Процессор | Память |
|---|---|---|
| Окно открыто, источников нет | 0,07 % | 92 МБ |
| Одна запись, точная модель + позы | 21 % | 435 МБ |
| Три записи, быстрая модель + позы | ~35 % | ~410 МБ |
| IP-камера 1080p, точная модель + позы | ~16 % | 594 МБ |

### Отставание рамки от человека — УСТРАНЕНО 6 сентября 2026

Заказчик пожаловался: рамка вокруг человека сильно отстаёт от картинки.
Разбор показал три причины, и главная оказалась не там, где искали.

| Что | Было | Стало |
|---|---|---|
| Обновлений рамки в секунду (одна камера) | 2,5 | **7,6** |
| То же на двух камерах | 2,5 | **6,1** |
| Время разбора кадра, две камеры | 204 мс | **178 мс** |

**Причина первая, главная: искусственная пауза.** `detectIntervalMs` был равен
400 мс — два с половиной разбора в секунду при видео в тридцать кадров. Сам
разбор занимал вдвое меньше, остальное время поток простаивал. Стало 120 мс.

**Причина вторая: модели работали в два потока.** В коде стояло `cpuThreads = 2`
с пометкой «больше двух не даёт выигрыша». Замер на настоящем кадре это
опроверг:

| Потоков | YOLOX-s | YOLOX-tiny | RTMPose (3 человека) |
|---|---|---|---|
| 2 | 144,1 мс | 44,0 мс | 69,7 мс |
| **4** | **86,6 мс** | **27,1 мс** | **40,7 мс** |
| 8 | 89,8 мс | 32,1 мс | 43,4 мс |

Четыре — измеренный оптимум: на восьми накладные расходы съедают выигрыш.

**Причина третья: позы считались так же часто, как искались люди.** На кадре с
шестью людьми поиск занимает 87 мс, а позы — 117 мс, то есть позы дороже всего
остального вместе взятого. При этом ни одно правило не смотрит на отдельный
кадр: самый короткий порог — две секунды. Теперь позы считаются раз в 300 мс, а
рамки обновляются на каждом разборе.

Чтобы вердикт при этом не мигал, между разборами поз он берётся из последнего:
рамка сопоставляется с прежней по перекрытию (`core::matchPrevious`, порог 0,5
площади). Закреплено проверкой `verdictSurvivesBetweenPoseRuns`.

**Скелеты больше не рисуются.** По прямому указанию заказчика: оператору нужна
рамка и вердикт словами, а семнадцать точек с линиями — отладочная картинка.
Пункт меню «Показывать скелеты» остался, по нему проверяют биомеханику.

**Цена — нагрузка.** Одна камера: ~46 % процессора, две: ~60 %. Раньше было
16 % на камеру. Это плата за своевременность; темп настраивается оператором
(«Настройки → Распознавание»), а на слабом компьютере есть быстрая модель.

**Настройки переводятся на новый темп сами.** Файл настроек перекрывает
умолчания программы, поэтому улучшение до уже работающего объекта не доехало бы
никогда. Добавлено поле `версия_настроек`: при версии ниже второй значение 400
заменяется на 120. Значение, выбранное оператором вручную, не трогается.

## 7. Правила распознавания и спорные случаи

Пять правил: **завис в воде**, **лежит без движения**, **упал и не встаёт**,
**ребёнок без присмотра**, **неуверенная походка**. Три уровня: НОРМА /
ВНИМАНИЕ / ТРЕВОГА. Каждый вердикт несёт список причин обычными словами.

### Загорающий на лежаке

Загорающий и человек без сознания на снимке **одинаковы**. Отличить нельзя ни
человеком, ни машиной. Терпение разведено по обстановке:

| Где | Внимание | Тревога |
|---|---|---|
| В воде | 2 с | **4 с** |
| На суше | 30 с | 180 с |

Потерявшего сознание на бортике ловит правило «упал и не встаёт»: оно требует
**резкого** перехода в горизонталь. Загорающий ложится плавно.

### Спящий взрослый — не присмотр

Случай из практики: мать спала на лежаке, дочь утонула. Формально взрослый был
рядом, фактически ребёнок был один. Присматривающим считается только тот, кто
двигался последние **20 секунд**. Ребёнок в воде + неподвижный взрослый рядом =
**тревога**, и её не глушит даже общий запрет тревог по признаку ребёнка.

### Отметка «панель смотрит на воду»

Задаётся оператором в настройках. Пока не отмечена, водные правила молчат
вовсе. Без этого «не видно ног» считалось водой, и сидящий за столом человек
получал тревогу «ребёнок в воде».

### Восемь классов ложных срабатываний, уже закрытых

Все закреплены проверками в `tests/test_core.cpp` — поднимая
чувствительность, нельзя молча вернуть их обратно.

1. «Неуверенная походка» у прохожих → туловище не мельче 60 точек, путь не
   короче двух длин тела.
2. «Ребёнок в воде» на сидящем за столом → отметка воды.
3. Одинокий взрослый как ребёнок → порог 0,50, полоса правдоподобия до 0,60,
   тревога по признаку ребёнка запрещена до калибровки на детях.
4. Дальний взрослый как ребёнок → рост перестал быть поводом (камера не знает
   расстояния).
5. Загорающий → разные пороги в воде и на суше.
6. Спящий взрослый → требование подвижности.
7. Длительности по истории 15 с → накопительный счёт.
8. «Видеть фигуру целиком» блокировало ребёнка в воде → заменено на отношение
   длины туловища к ширине плеч.

Плюс тихая поломка: **настройки не читались** — русские ключи JSON
сравнивались через `QLatin1String` (UTF-8 байты ≠ Latin-1 символы). Программа
работала на значениях по умолчанию.

## 9. IP-камера на нестандартном порту — ИСПРАВЛЕНО 6 сентября 2026

Заказчик поднял запасной смартфон в режиме IP-камеры (приложение «IP Webcam»),
**`http://192.168.1.126:8080/`**. Программа её не находила и подключить не
давала. Причин было три, все в нашем коде, и все закрыты.

### Что оказалось на самом деле — по измерениям

Смартфон отдаёт по одному порту **8080** сразу два потока. Оба проверены живым
подключением через тот же `QMediaPlayer`, которым пользуется `NetworkSource`:

| Поток | Адрес | Первый кадр | Частота | Формат |
|---|---|---|---|---|
| MJPEG | `http://192.168.1.126:8080/video` | 0,07 с | 24,9 кадр/с | mjpeg 1920×1080 |
| RTSP | `rtsp://192.168.1.126:8080/h264_ulaw.sdp` | 1,99 с | 22,6 кадр/с | H.264 High + звук |

Открыт **только 8080**: ни 554, ни 80, ни 8554. Поле `rtsp_video_formats` в
`status.json` при этом пустое — **оно не показатель**, RTSP работает.

**Основным сделан RTSP.** Он втрое легче для сети, чем MJPEG на 1080p, и его же
понимает Media3/ExoPlayer в будущем приложении для Android. MJPEG оставлен
запасным: включается мгновенно и не требует от камеры кодировщика.

**`NetworkSource` менять не пришлось.** Предположение подтвердилось замером:
FFmpeg-бэкенд Qt разбирает MJPEG по HTTP сам, демультиплексором `mpjpeg`.

### Что исправлено

1. **Поиск смотрит список портов**, а не один 554: RTSP — 554 и 8554, HTTP —
   8080, 8000, 88, 81. Порт 80 намеренно не опрашивается: его слушает всё
   подряд, и список находок стал бы перечнем роутеров и принтеров.
2. **Схема выбирается** — `rtsp://` либо `http://`. В окне подключения
   появился выбор протокола, а `buildUrl()` больше не навязывает `rtsp`.
3. **Есть шаблоны под смартфон** — два: H.264 и MJPEG.
4. **Адрес принимается целиком.** Вставленную ссылку окно само разбирает по
   полям. Разбор идёт по завершении ввода, а не на каждой букве, — иначе на
   третьем символе строки «http://192…» поле схлопывалось бы в «1».
5. **Ключ `--panelN` принимает адрес потока**, а не только файл и камеру.

### Две ошибки, вскрытые уже живым поиском

Первый же настоящий запуск дал **206 находок вместо одной**. Обе причины —
наши, и вторая была в коде с самого начала.

1. **Сеть `/30` опрашивалась как `/24`.** Код отбрасывал сети шире `/24`, но
   дальше всё равно маскировал адрес до `x.x.x.0` и перебирал 254 узла. На
   компьютере оператора поднят туннель VPN — сеть `172.18.0.1/30`, четыре
   адреса, — и опрашивалось 254 вместо двух. Теперь диапазон считается по
   настоящей длине префикса.
2. **Открытый порт RTSP принимался за камеру на веру.** Туннель подтверждает
   соединение на любой адрес и порт, и список наполнялся сотнями камер,
   которых нет. Теперь по открытому порту задаётся запрос `OPTIONS` и ждётся
   ответ `RTSP/…`: так отвечает только настоящий RTSP-сервер, причём **до**
   проверки пароля — камера с неизвестным нам паролем всё равно назовётся.
   Для HTTP-портов отпечаток спрашивается запросом `/status.json`.

После правок: **1 находка вместо 206**, за 10,6 с.

### Как это выглядит теперь

Поиск находит камеру дважды — по ONVIF (приложение его поддерживает) и по
отпечатку — и подставляет **готовый адрес целиком**:

```
192.168.1.126 — IP_Webcam BUILD_913  [ONVIF; HTTP 8080]
        готовый адрес: rtsp://192.168.1.126:8080/h264_ulaw.sdp
```

### Проверено вживую

Программа запущена с живой камерой, снимок экрана подтверждает: поток идёт
(1920×1080, 30 к/с), человек найден, рамка и скелет нарисованы, счётчик «в
зоне: 1», сопровождение **43,7 с**.

```powershell
PoolSafety.exe --panel1 rtsp://192.168.1.126:8080/h264_ulaw.sdp
```

### Настройка смартфона для проверок

В приложении «IP Webcam» достаточно нажать «Запустить». Из настроек имеет
смысл поставить **разрешение 1280×720**: модель всё равно ужимает кадр до 640
точек, а 1080p зря грузит сеть и декодер. Ориентацию приложение применяет само
— в кадре программы изображение уже правильное, несмотря на `upsidedown` в
`status.json`.

## 10. Приложение для Android — СДЕЛАНО 6 сентября 2026

Папка `pool_safety_android`, пакет `ru.poolsafety.watch`, Kotlin, minSdk 26
(Android 8.0), targetSdk 34, версия 1.1.1. Подробности и грабли сборки — в
`pool_safety_android/README.md`.

### Что сделано и проверено вживую

Проверялось на эмуляторе Android 14 (API 34) при работающей программе на
компьютере. Каждый пункт подтверждён снимком экрана телефона.

| Требование заказчика | Состояние |
|---|---|
| Уведомления на каждый сигнал | сделано: «Человек в зоне — В зоне люди: 3» |
| Уведомление о тревоге | сделано: «ТРЕВОГА — Северо-восточный угол» с указанием, что делать |
| Просмотр: все четыре либо одна | сделано, переключение нажатием по клетке |
| Картинка в картинке | сделано, подтверждено `mode=pinned` |
| Цвет рамки по уровню | сделано: зелёный, оранжевый, красный (толще) |
| Настройки: звук, громкость, список угроз | сделано |
| Звуки встроенные в устройство | сделано, свои файлы не используются |
| Совместимость со старыми телефонами | minSdk 26 |

Поиск компьютера работает: телефон сам находит его широковещательным запросом
и подставляет адрес — на эмуляторе это `10.0.2.2`.

### Видео с камеры — проверено

Телефон берёт поток **напрямую с IP-камеры**, минуя компьютер: на панели
«Северо-западный угол» идёт та же картинка, что и на посту. Картинка в картинке
с живым видео тоже проверена — окно поверх рабочего стола, поток не прерывается.

Здесь нашлась ошибка, которую не увидеть чтением кода: **видео не успевало
начаться**. Сведения о панелях шлются при каждом изменении обстановки, то есть
в людной смене по нескольку раз в секунду, и каждое такое сообщение
перезапускало проигрыватель — в журнале шла бесконечная череда «создан —
освобождён». Теперь поток трогается только при смене адреса. Проверено
счётчиком: проигрыватель создаётся один раз за сеанс.

Попутно: надпись «подключение к камере…» висела поверх уже идущего видео —
состояния `READY` для живого потока мало, надпись снимается по первому
показанному кадру (`onRenderedFirstFrame`).

### Возобновление после перезагрузки

Телефон перезагружается сам: ночное обновление системы, разрядка, сбой. Если
после этого приложение молчит, пока его не откроют руками, наблюдение выключено
— и никто об этом не знает. Это худший вид отказа: он не виден.

`service/BootReceiver` поднимает службу по `BOOT_COMPLETED` и после обновления
самого приложения — но только если компьютер уже выбран. Проверено
перезагрузкой эмулятора: в журнале «после загрузки: поднимаем наблюдение», сразу
следом «компьютер представился: 1.1.0», приложение не открывали.

### Что НЕ проверено

**Настоящий телефон.** Всё проверено на эмуляторе Android 14.

### Три ошибки, найденные проверкой на эмуляторе

Ни одну из них нельзя было увидеть чтением кода.

1. **Приложение падало при сохранении настроек.**
   `ForegroundServiceDidNotStartInTimeException`: экран настроек посылал
   службе «остановись» и сразу «запустись», и `stopSelf()` от первой команды
   убивал службу уже после того, как вторая её подняла. Плюс ветка остановки
   вовсе не вызывала `startForeground()`, а Android даёт на это пять секунд и
   убивает приложение целиком. Теперь уведомление ставится первым действием,
   до разбора команды, а настройки шлют одну команду.

2. **Тревога, объявленная оператором вручную, до телефонов не доходила.**
   Телефонам сообщал только разбор кадра — то есть ровно тот случай, когда
   человек уже увидел беду, оставался без сигнала. Теперь рассылка идёт по
   сигналу `alarmRaised`, одному на все источники тревоги. Заодно: когда
   автотревога выключена (режим настройки на новом объекте), телефон получает
   «внимание», а не тревогу — иначе он выл бы сиреной там, где на посту её нет.

3. **Красная рамка гасла через секунду.** Следом за событием приходил список
   панелей с уровнем от разбора кадра и затирал тревогу. Теперь объявленная
   тревога главнее разбора: панель числится в тревоге, пока оператор её не
   закроет.

Плюс две недоработки поменьше: телефон не знал, **на какой панели** люди
(список панелей рассылался только при смене источника), и рамка не красилась у
панелей без видео — а тревога на такой панели выглядела как пустая клетка.

### Про MJPEG

**ExoPlayer формат MJPEG не понимает вовсе.** Пришлось написать свой приёмник
(`ui/MjpegView.kt`): HTTP multipart, поиск маркеров `FF D8` и `FF D9`, разжатие
сразу до размера клетки. Без него запасной поток смартфона показывал бы
«формат не поддерживается» там, где картинка есть.

### Окружение сборки

Android SDK установлен на **`D:\Android\Sdk`** (5,6 ГБ), Gradle 8.7 — на
`D:\Android\gradle-8.7`. На системном диске оставалось 15 ГБ, туда бы не влезло.
Эмулятор `poolsafety` создан.

## 11. Что исправлено в 1.1.1

Всё найдено заказчиком при работе с выпуском 1.1.0.

### Отключённый источник продолжал показывать картинку

Оператор выбирал «Отключить источник», пункт из меню исчезал, панель считала
себя пустой — а видео продолжало идти. Для поста наблюдения это худший вид
ошибки: на экране живая камера там, где наблюдения уже нет.

Причина в `CameraPanel::detachSource()`: рвалась только связь источника с самой
панелью, а кадры и состояние идут ещё и **напрямую в вид**. Теперь
отсоединяются оба получателя.

### Тревогу нельзя было выключить с телефона

Спасатель с телефоном в руках у самой воды видел тревогу, но погасить сирену
мог только тот, кто стоит у компьютера. Канал был односторонним.

Теперь он двусторонний: телефон присылает те же три решения, что доступны
оператору на посту — «принял», «ложная», «подтверждаю». Особых прав у телефона
нет, придумывать для него отдельные решения нельзя: спасатель и оператор
должны понимать друг друга.

```json
{"type":"command","action":"acknowledge"}
```

### Уведомление о тревоге не снималось

Тревогу погасили на посту, а на телефоне она висела красным до следующего
события. Спасатель считал, что беда продолжается.

Добавлено сообщение о состоянии тревоги — телефон узнаёт о снятии сразу:

```json
{"type":"alarm_state","state":"idle","panel":2}
```

### Связь рвалась при каждом открытии экрана

`MainActivity.onStart` просил службу начать наблюдение, а та первым делом
закрывала работающее соединение и устанавливала заново. В журнале «Socket
closed», на экране «нет связи», а тревога, пришедшая в эту секунду, попадала в
разрыв. Теперь живая связь к тому же компьютеру не трогается.

### Видео на телефоне отставало на десятки секунд

ExoPlayer по умолчанию копит до **пятидесяти секунд** видео: для фильма это
правильно, для наблюдения — катастрофа. Буфер урезан до долей секунды
(200/800/100/150 мс). Картинка может дрогнуть при заминке сети — это
несравнимо меньшая беда, чем отставание.

### Версия обновляется, а не ставится второй копией

У установщика постоянный `AppId`, `AppMutex=PoolSafetyRunning` и
`CloseApplications=yes`: он закрывает работающую программу и обновляет её на
месте. У приложения `versionCode` поднят с 1 до 2 — без роста этого номера
Android не поставит обновление поверх, и заказчик остался бы со старой
сборкой, думая, что обновился. Проверено обновлением 1.1.0 → 1.1.1 без
удаления: настройки сохранились.

## 12. Что добавлено в 1.2.0

### Счёт людей — по самой многолюдной камере, а не суммой

Четыре камеры смотрят на одну чашу с разных сторон. Человек у воды виден сразу
с нескольких, и сложение превращало его в четверых: оператор читал «в зоне
людей: 8» там, где их двое. Счётчику, который врёт втрое, перестают верить
целиком — а он и есть сигнал присутствия.

Максимум занижает счёт, когда люди в разных концах чаши и каждая камера видит
своих. Это осознанный выбор: завышенный счёт врёт всегда, заниженный — только
в редком случае, и ни одно правило от него не зависит (правила работают по
дорожкам людей внутри своей панели).

### Тревогой можно управлять с телефона полностью

Добавлена команда «происшествие закрыто». Раньше «помощь вызвана» переводила
тревогу в состояние вызова, а закрыть его с телефона было нечем — и кнопка
выглядела неработающей. Теперь набор кнопок меняется по состоянию:

| Состояние | Кнопки на телефоне |
|---|---|
| объявлена | принял · ложная · помощь вызвана |
| принята | ложная · помощь вызвана |
| помощь вызвана | происшествие закрыто |

Телефон, подключившийся уже посреди происшествия, узнаёт о нём сразу: состояние
тревоги отправляется новому клиенту вместе со списком панелей.

### Звук тревоги на телефоне больше не сбрасывается касанием

Уведомление звучит один раз, при показе, и обрывалось от первого касания
шторки: звук пропал, а решения никто не принял. Теперь звук даёт своя сирена
(системный сигнал будильника, зациклен) и звучит, пока человек не ответит.

В самом уведомлении две кнопки, и разница между ними важна:

- **«Заглушить»** — выключает звук ТОЛЬКО на этом телефоне. Тревога на посту
  продолжается, уведомление остаётся. Это для того, кто уже бежит к бассейну.
- **«Принять»** — тоже выключает звук и открывает приложение на нужной камере,
  где есть три решения.

Ни одна из них не снимает тревогу: кнопка в шторке для этого слишком легко
нажимается случайно. Уведомление тревоги не смахивается.

Кнопка «Принять» открывает экран напрямую, а не через приёмник: начиная с
Android 10 приложению запрещено открывать окна из фона — приёмник отрабатывал,
писал в журнал, а экран не появлялся.

### Приближение двумя пальцами

Щипок приближает картинку выбранной камеры до четырёхкратного, перетаскивание
двигает её, двойное нажатие возвращает к исходному. Одиночное нажатие
по-прежнему разворачивает камеру на весь экран и обратно.

Приближение не трогает распознавание: оно происходит целиком на телефоне и
только для глаз — компьютер разбирает полный кадр. В картинку в картинке
уходит та камера, которую разворачивали последней.

### Карта постоянного окружения («самообучение»)

**Это не дообучение нейросети, и это важно.** Дообучать распознавание людей на
объекте нельзя: нужна разметка «здесь человек, здесь нет», которой взять
неоткуда, а самообучение детектора без разметки неизбежно сползает в
деградацию — модель начинает пропускать людей, и узнают об этом на настоящем
происшествии.

Что сделано вместо этого — статистика по кадру, классика компьютерного зрения.
Кадр делится на сетку 32×18, и для каждой клетки копится одно число:
насколько она обычно меняется от разбора к разбору. Плитка на дне, стена,
дверной проём меняются почти никак. Дорожка, где ходят люди, — постоянно.

**Копится изменчивость, а не цвет.** Цвет зависит от света: к вечеру картинка
темнеет, и модель, запомнившая дневные цвета, объявила бы чужим весь кадр
разом. Изменчивость от света почти не зависит — солнце садится медленно и
всюду, а человек проходит быстро и в одном месте.

**Как используется.** Модель НЕ подавляет обнаружение людей. Она лишь повышает
требуемую уверенность там, где неделями не менялось ничего: слабый отклик на
стене — почти наверняка узор или тень. Уверенный отклик проходит всегда:
человек может стоять неподвижно, и в мёртвом углу кадра он тем более важен.

**Если сцена изменилась, модель молчит.** Она сравнивает накопленное с тем, что
видит последние минуты, и при расхождении отключается сама. Опираться на
устаревшую карту опаснее, чем не иметь никакой.

| Что | Значение |
|---|---|
| Файл | `config/окружение.json` рядом с настройками, свой у каждой установки |
| Обучение | около часа непрерывной работы до первой пользы |
| Забывание | половина за час — лежак переставляют реже, чем на нём спят |
| Отключается сама | если совпадение со сценой ниже 35 % |

В настройках: выключатель (по умолчанию включён), подсказка при наведении,
состояние обучения словами, «начать заново» и «загрузить готовое».

### RTSP и смартфон-камера: почему поток пропадал

Камера находилась, соединение устанавливалось, а кадров не было — панель молча
переподключалась. Со стороны это выглядит как «программа не видит камеру»,
хотя видит.

**Причина в устройстве самого RTSP.** Он договаривается по TCP, а видео шлёт
отдельными пакетами UDP. TCP до камеры доходит: на проверке соединение с
портом 8080 устанавливалось напрямую через Ethernet, маршрут `192.168.1.0/24`
локальный, VPN его не трогает. А вот пакеты с видео теряются — и достаточно
любой из двух причин:

- включённая VPN держит маршрут по умолчанию через туннель;
- у компьютера **два сетевых адреса в одной подсети** (Ethernet 192.168.1.91 и
  Wi-Fi 192.168.1.108), и ответные пакеты приходят не на тот, что просил.

Точную из двух причин выделять не понадобилось: решение одно и снимает обе.

**Проверено на двух панелях одновременно.** Одной дали `rtsp://…8080/h264_ulaw.sdp`,
другой `http://…8080/video`. Первая — «переподключение (попытка 6)», вторая —
«1280×720, 25 к/с, поток идёт».

**Что сделано.**

1. При обнаружении смартфон-камеры подставляется **MJPEG**, а не H.264. Раньше
   программа сама выбирала RTSP — то есть сама вела оператора в неработающую
   настройку.
2. В списке готовых адресов MJPEG стоит первым.
3. Если заданный оператором RTSP молчит три попытки подряд (около десяти
   секунд), программа **сама переходит на MJPEG** и пишет об этом в подписи
   панели. Это спасает уже настроенные объекты: там адрес сохранён в файле
   настроек, и никакое новое умолчание до них бы не дошло.

Запасной путь известен только для смартфона: он один отдаёт оба вида потока по
одному порту. Для обычных камер путь у каждого производителя свой, и
угадывание дало бы оператору ложную надежду вместо честного «связи нет».
Закреплено проверкой `rtspFallsBackToHttpForPhoneCamera`.

**Цена.** MJPEG тяжелее для сети: кадры идут без межкадрового сжатия. На
локальной сети это несущественно, а взамен поток включается мгновенно (по
прежнему замеру — 0,07 с против 1,99 с у RTSP) и доходит везде, куда доходит
страница камеры.

## 13. Что добавлено в 1.3.0

### Репозиторий на GitHub

Проект выложен на **github.com/pypistypi/pool-safety** — открытый исходный
код, установщик и APK каждого выпуска в разделе Releases. README со ссылками
на скачивание сделан отдельно от этого справочника: он короткий и рассчитан
на заказчика, а не на продолжение разработки.

Модели ONNX (113 МБ) и `onnxruntime.dll` включены в репозиторий — без них
исходный код не собрать. Готовая поставка (`dist/`) в git не хранится:
слишком тяжёлая и пересобирается при каждом выпуске — она уходит только в
Releases.

### Кнопка «Отключиться» на телефоне

Заказчик пожаловался: приложение шлёт уведомления о неудачном подключении,
даже когда телефон уходит за пределы домашней сети. Причина в том, что
раньше отключить приложение от поста было нечем: `WatchService.start()`
вызывался безусловно при каждом открытии экрана, и служба пыталась
связаться бесконечно — сеть локальная, снаружи достучаться нельзя ни за что.

Добавлен переключатель «Отключиться» / «Подключиться» рядом со строкой связи
на главном экране. При отключении: `Prefs.manuallyDisconnected = true`,
служба останавливается, постоянное уведомление снимается. Флаг проверяется
в трёх местах — при открытии экрана, при получении события от
`BootReceiver` и **внутри самой службы** (`beginWatching()`): служба
помечена `START_STICKY`, и если систему прижмёт по памяти, она поднимется
заново сама с тем же действием по умолчанию, минуя экран. Без проверки на
третьем месте отключённый оператором телефон снова начал бы ломиться на
пост после первой же чистки памяти.

**Побочная находка при проверке — настоящая гонка.** `client.stop()` меняет
состояние связи на `Offline`, а на него подписан отдельный слушатель,
вызывающий `NotificationManager.notify()` напрямую, в обход
`stopForeground()`. Слушатель работает в своей корутине и иногда успевал
сработать ПОСЛЕ `stopForeground(STOP_FOREGROUND_REMOVE)`, переиздавая
уведомление службы уже после его удаления: `dumpsys activity services`
показывал, что служба остановлена (`ServiceRecord` пуст), а
`dumpsys notification` — что уведомление с флагом `FOREGROUND_SERVICE`
всё ещё висит. Со стороны оператора это выглядело как очередной сбой.
Исправлено флагом `stopping` (`@Volatile`), который выставляется ДО
`client.stop()` и проверяется в начале `updateServiceNotification()`, плюс
явная `manager.cancel(ID_SERVICE)` в конце — на случай, если слушатель успел
проскочить до того, как флаг стал виден его потоку.

Заодно короткие, человеческие сообщения о разрыве связи вместо сырого текста
исключений Java (`failed to connect to /10.0.2.2 (port 8765) from
/10.0.2.16 (port 42342) after 5000ms: isConnected failed: ECONNREFUSED…` →
«компьютер не запущен или порт закрыт»).

### Проверка обновлений

`UpdateChecker` спрашивает `api.github.com/repos/pypistypi/pool-safety/
releases/latest`, сравнивает тег с `BuildConfig.VERSION_NAME` числами по
частям (не строкой: «1.9.0» строкой больше «1.10.0», а по смыслу меньше),
и при отставании показывает диалог с кнопкой «Скачать» — она открывает
браузер на прямой ссылке на APK. Скачивание идёт через браузер, а не внутри
приложения: свой загрузчик потребовал бы разрешения «устанавливать
неизвестные приложения» и обработки файлового провайдера, а браузер и
системный загрузчик делают это надёжно и без нашего участия.

Проверяется автоматически раз в сутки при открытии приложения (не чаще —
открывают его по многу раз за смену) и по кнопке «Проверить сейчас» в
настройках без ограничения по времени. Переключатель в настройках, включён
по умолчанию.

**Это единственное место во всём приложении, где есть обращение в
интернет.** Несущий принцип — связь с постом наблюдения только по локальной
сети, без интернета и облаков — не тронут: проверка обновлений отдельная и
отключаемая, ошибка сети в ней тихая (как будто обновлений не нашли, а не
повод для тревожного сообщения), и не запускается сама по себе фоново —
только когда оператор открыл приложение.

Проверено вживую подменой версии на заведомо старую: диалог показал
«Версия 1.2.1. У вас установлена 1.0.0», кнопка «Скачать» открыла браузер
на `github.com/…/releases/download/v1.2.1/PoolSafetyWatch-1.2.1.apk`.

## 15. Правила работы над проектом

- **Русский язык везде**: интерфейс, комментарии, документы, общение.
  Орфография строгая, с ё.
- **Проверять измерением, а не утверждением.** Замер CPU через
  `TotalProcessorTime`, отрисовку — снимком экрана, распознавание — на
  настоящих кадрах.
- **Ложная тревога дороже пропущенной, если она частая.** За смену она
  приучает оператора не верить сирене.
- **Признак, не проверенный на настоящем случае, не получает права на сирену.**
- **Не обещать того, чего система не делает.** Формулировки в интерфейсе и в
  документах уже выверены — не «распознаёт утопление», а «не даёт остаться
  незамеченным».
- Каждое исправление ложного срабатывания закрепляется проверкой в
  `tests/test_core.cpp`.
