## 0.0. Два вида сигналов — сквозной принцип всех трёх этапов

Полное описание — в ТЗ, п. 1.6, 3, 6.3. Кратко, в терминах разработки:

| | **Сигнал 1 — ПРИСУТСТВИЕ** | **Сигнал 2 — ТРЕВОГА** |
|---|---|---|
| Что означает | В зоне бассейна (чаша + прилегающая территория) есть ≥ 1 человек; все они взяты на сопровождение | По конкретной сопровождаемой цели распознаны признаки утопления/потери сознания |
| Целей | Неограниченно | Возможно несколько одновременно |
| Действие оператора | Не требуется | Обязательное подтверждение + обязательное решение |
| Таймер и автодозвон | **Никогда** | Да |
| Контракт данных | `TrackedPerson`, `PresenceSnapshot` | `ClassificationResult` → `AlertEvent` |
| Кто порождает на Этапе 1 | Заглушка присутствия (Код 48) | Заглушка-кнопка (Код 9) |
| Кто порождает на Этапе 2 | Детектор + трекер (Коды 28, 30) — **готовые предобученные веса, обучение не требуется** | Обученный классификатор (Код 36) |

**Ключевое следствие для планирования:** Сигнал 1 технически проще Сигнала 2 и не зависит от сбора данных и обучения — для него достаточно детектора людей общего назначения. Поэтому в Этапе 2 он выносится в отдельный ранний шаг (2.1а) и становится рабочим задолго до того, как будет готов алгоритм распознавания утопления. Это же означает, что промежуточная версия системы, полезная заказчику, появляется раньше: оператор уже видит реальных людей на реальном видео и сопровождает их, а тревогу пока объявляет сам кнопкой.

**Жёсткое правило, действующее на всех этапах:** присутствие людей **никогда** не запускает таймер подтверждения и **никогда** не приводит к автодозвону. Любой код, где сигнал присутствия способен попасть в машину состояний тревоги или в `EscalationManager`, считается дефектом, а не особенностью реализации.

## 0. Три этапа — общая логика

| Этап | Что делаем | Что на выходе |
|---|---|---|
| **Этап 1** | Программа целиком: интерфейс оператора, **оба сигнала** — присутствие и тревога, вся логика тревоги, эскалация, вызов данных для 112. Камера — заглушка (фото + дата/время). Присутствие — заглушка (кнопки «+/− человек» задают число сопровождаемых целей). Тревога — заглушка (кнопка вручную симулирует "алгоритм только что распознал тонущего"). | Полностью рабочая программа, кроме "мозга" (реального распознавания) и реального видео |
| **Этап 2** | Сначала — реальное сопровождение людей на живом видео (Сигнал 1, готовые веса детектора, Шаг 2.1а). Затем — разработка и обучение настоящего алгоритма распознавания тонущего человека (Сигнал 2). | Сначала — работающее реальное присутствие; затем обученная модель, которая на выходе даёт то же самое событие тревоги, что раньше давала кнопка — просто автоматически |
| **Этап 3** | Физический монтаж: камеры, коммутатор, рабочий ПК, сеть, электропитание, интеграция готового ПО (Этап 1) с готовым алгоритмом (Этап 2) на реальном объекте. | Работающая система на объекте |

**Ключевой архитектурный принцип, который делает это возможным без переделок:** уже на Этапе 1 обе "заглушки" (камера и тревога) реализуются не как случайный временный код, а как конкретная реализация заранее описанного **абстрактного интерфейса**. Реальная камера (Этап 3) и реальный алгоритм (Этап 2) будут реализовывать те же самые интерфейсы. Замена происходит на уровне конфигурации (одна строчка — какая реализация активна), а не переписыванием логики. Это тот же принцип "скелет → мышцы", что и в плане v1, просто теперь явно разбитый по этапам с понятными точками сдачи.

### 1.1. Контракты Сигнала 1 — присутствие и сопровождение (новое в v2.1)

```python
from dataclasses import dataclass, field
from typing import Literal

@dataclass
class TrackedPerson:
    """Одна сопровождаемая цель. Порождается заглушкой присутствия
    (Этап 1, Код 48) или реальным трекером (Этап 2, Код 30) — остальная
    система не различает источник.

    ВАЖНО (152-ФЗ, ТЗ п.4.3): track_id — временный технический номер
    трека внутри текущей сессии наблюдения. Он НЕ связывается с
    личностью, не сохраняется между визитами и не является
    биометрическим идентификатором."""
    track_id: int
    camera_id: str
    bbox: tuple[float, float, float, float]
    in_water: bool           # см. ТЗ п.6.7 — определяет, применять ли к цели классификатор утопления
    status: Literal["OK", "ALERT"]
    first_seen_ts: float
    last_seen_ts: float

@dataclass
class PresenceSnapshot:
    """Мгновенный срез присутствия по одной камере — то, что интерфейс
    оператора рисует как зелёные рамки и счётчик целей."""
    camera_id: str
    zone_label: str
    persons: list[TrackedPerson] = field(default_factory=list)
    ts: float = 0.0

    @property
    def count(self) -> int:
        return len(self.persons)

@dataclass
class ZoneState:
    """Агрегированное состояние всей зоны бассейна — источник Сигнала 1
    для оператора. Меняется EMPTY <-> OCCUPIED; переход EMPTY -> OCCUPIED
    сопровождается однократным мягким звуком и записью в журнал."""
    state: Literal["EMPTY", "OCCUPIED"]
    total_persons: int
    per_camera_counts: dict[str, int]
    changed_ts: float
```

### 1.2. Контракты Сигнала 2 — тревога и эскалация

```python
from dataclasses import dataclass
from typing import Literal

@dataclass
class Detection:
    camera_id: str
    frame_ts: float
    track_id: int
    bbox: tuple[float, float, float, float]
    confidence: float

@dataclass
class ClassificationResult:
    """И кнопка-заглушка (Этап 1), и обученная модель (Этап 2) обязаны
    выдавать результат ИМЕННО в этом формате — это и есть точка стыковки этапов."""
    track_id: int
    camera_id: str
    status: Literal["OK", "ALERT"]
    reason: str          # например "manual_trigger" на Этапе 1, "no_movement_12s" на Этапе 2
    confidence: float
    ts: float

@dataclass
class AlertEvent:
    """ИЗМЕНЕНО в v2.1: тревога привязана к КОНКРЕТНОЙ ЦЕЛИ (track_id),
    а не к камере целиком. Это обязательное следствие Сигнала 1: на
    одной камере одновременно сопровождается сколько угодно людей, и
    тревога по одному из них не должна влиять на остальных, а вторая
    тревога на той же камере не должна затирать первую.

    ДОБАВЛЕНО: acknowledged_ts — момент, когда оператор нажал
    "Подтверждаю получение". Именно он останавливает таймер эскалации,
    а не выбор окончательного решения (ТЗ, п.6.2)."""
    event_id: str
    camera_id: str
    track_id: int
    zone_label: str
    start_ts: float
    status: Literal[
        "NEW", "AWAITING_OPERATOR", "ACKNOWLEDGED", "CONFIRMED_FALSE",
        "CONFIRMED_REAL", "ESCALATED", "CLOSED"
    ]
    acknowledged_ts: float | None = None

@dataclass
class IncidentInfo:
    """ИЗМЕНЕНО в v2.1: victims_count вычисляется как число целей в
    статусе ALERT на момент вызова (было захардкожено = 1).
    ДОБАВЛЕНО persons_in_zone — общее число людей в зоне из Сигнала 1;
    диспетчеру важно знать, один ли пострадавший в пустом бассейне
    или инцидент в многолюдной зоне (ТЗ, п.6.4)."""
    address: str
    zone_label: str
    start_ts: float
    duration_sec: float
    description: str
    victims_count: int
    persons_in_zone: int
    callback_phone: str

@dataclass
class EscalationState:
    event_id: str
    attempts: list[dict]
    acknowledged: bool

@dataclass
class CameraFrame:
    """И фото-заглушка (Этап 1), и живой RTSP-поток (Этап 3) обязаны отдавать
    кадр именно в этом формате — вторая точка стыковки этапов."""
    camera_id: str
    zone_label: str
    image: bytes          # JPEG/PNG кадра (статичное фото или кадр из потока)
    captured_ts: float     # время получения кадра — на заглушке это текущее время сервера
```

| «Битые символы слева от времени» | `PIL.ImageFont.load_default()` содержит только латиницу | Системный TrueType-шрифт с кириллицей и запасными вариантами (Код 64) |

Дополнительно найдено и исправлено при проверке:

- **OpenCV не открывает ONNX-модели по путям с кириллицей**, а проект лежит
  в папке «ИИ наблюдение». Модель загружается через буфер в памяти. То же
  повторилось бы у заказчика при установке в папку с русским именем.
- **WebSocket-соединения терялись при смене режима**: менеджер соединений
  принадлежал контексту, а тот пересобирается. Картинка продолжала идти, а
  счётчик людей и состояние зоны замирали навсегда — самый опасный вид
  отказа, молчаливый. Менеджер сделан общим на приложение.
- **Системное окно с сообщением об ошибке блокировало программу** —
  показывается в отдельном потоке.

### Шаг 1.13 — Перевод программы на C++ / Qt 6

**Причина.** Реализация на Python исчерпала себя. Схема «интерпретатор +
OpenCV + веб-интерфейс во встроенном браузере» требовала на каждый кадр
распаковать JPEG, обработать его интерпретатором, снова сжать и передать
браузеру. Даже без распознавания это занимало процессор на 34–98 % и давало
рывки; каждая следующая оптимизация выигрывала всё меньше. Дальнейшие вложения
в эту схему окупаться перестали.

**Что сделано.** Программа переписана заново на C++ с Qt 6.11.1 (MinGW).
Каркас без распознавания: сетка из четырёх панелей, выбор источника для каждой
клетки, ручное объявление тревоги и её обработка. Исходники —
`pool_safety_qt/`, поставка — `pool_safety_qt/dist/PoolSafety/`.

| Решение | Обоснование |
|---|---|
| Декодирование средствами Qt | аппаратное декодирование Windows вместо покадровой работы интерпретатора |
| Собственный виджет вывода вместо `QVideoWidget` | штатный выводит картинку в отдельное системное окно, поверх которого Windows не рисует подписи; нам нужны поверх видео название зоны, время, счётчик людей и рамка тревоги |
| Реестр разделяемых источников (`SourceHub`) | один источник разрешено выбрать в нескольких клетках; открывается он при этом один раз — иначе вторая панель осталась бы без картинки (камеру дважды Windows не открывает) |
| Предел частоты показа 25 к/с | лишние кадры отбрасываются до всякой обработки |
| Невидимая панель не обрабатывает кадры | свёрнутое окно не стоит ничего |
| Разрешение камеры ограничено 1280×720 | камеры вроде Logitech BRIO стартуют в 4K, и весь этот кадр пришлось бы принять и разжать ради панели в четверть экрана |
| Отдельный поток разбора кадров (`AnalysisWorker`) | место под распознавание проведено сразу: приделать разделение задним числом означало бы переписывать и панели, и обмен данными |
| В потоке разбора одна ячейка на панель | новый кадр вытесняет необработанный: очередь иначе растёт без конца, съедая память и показывая всё более старую картинку |

**Замерено** (8 ядер, собранная программа):

| Режим | Процессор | Память |
|---|---|---|
| Окно открыто, источники не выбраны | 0,07 % | 92 МБ |
| Две записи + две камеры одновременно | 2,2 % | 172 МБ |
| То же через 2 минуты работы | 2,5 % | 138 МБ |

Проверено живым запуском: зацикливание записи (900 кадров за 90 с на файле
длиной 79 с), освобождение камер при закрытии, штатный выход за 1 с,
отсутствие роста памяти за длительный прогон. Ядро покрыто 15 автотестами
(`pool_safety_qt/tests/test_core.cpp`) — оба сигнала, порядок обработки
тревоги, разделение источников, вытеснение кадров.

**Отличие от прежнего интерфейса.** Переключатель режимов А/Б/В убран.
Источник выбирается для каждой клетки отдельно — файл с компьютера (видео или
фотография) либо любая камера компьютера. Это ближе к боевому сценарию, где у
каждой панели свой поток, и снимает надобность в отдельных режимах-заглушках.

**Не переносилось на этот шаг:** распознавание человека, водный полигон,
многокамерное подтверждение, дозвон и журнал инцидентов. Всё это ложится
на подготовленные границы следующими шагами.

### Шаг 1.14 — Распознавание человека в кадре и осмысленная тревога

**Распознавание.** Заказчик передал готовый алгоритм (`pool_safety_qt/person_detection_demo/`,
Python + ONNX Runtime + OpenCV, модель YOLOv5n). Алгоритм перенесён на C++
**без изменения самого метода**: та же модель `models/yolov5n.onnx`, та же
подготовка кадра (640×640, RGB, деление на 255), те же пороги (0,45 по
уверенности и по перекрытию), тот же класс COCO 0. Оставить его на Python
значило бы вернуть в петлю обработки кадров интерпретатор — причину, по
которой Этап 1 и переписывался (Шаг 1.13).

| Решение | Обоснование |
|---|---|
| ONNX Runtime подключается по имени файла во время работы | сборке MinGW не нужна библиотека импорта от чужого компилятора; отсутствие DLL не роняет программу, а даёт объяснение на экране |
| Заголовок Microsoft взят без правок, совместимость вынесена в `ort_compat.h` | при обновлении библиотеки заголовок заменяется перезаписью файла |
| Разбор — не чаще 3 раз в секунду на панель | прогон модели стоит 40 мс; человек не появляется за тридцатую долю секунды |
| Панели разбираются по очереди, одним потоком, модели дано 2 ядра из 8 | четыре параллельных прогона отняли бы ядра у отрисовки |
| Появление подтверждается двумя разборами, пропажа выдерживается 1,5 с | модель изредка теряет человека на кадре: без сглаживания счётчик прыгает, рамка мигает, звук тарахтит |
| Рамки и счётчик — один сигнал `panelAnalysed` | порознь панель перерисовывается между ними, показывая три рамки при счётчике «2» |

**Сигнал 1 доведён до вида, который просил заказчик.** Появился человек —
зелёные рамки на людях, зелёная рамка панели, плашка «В зоне: N», мягкий
звуковой сигнал и текстовая строка. Людей нет — **ничего**: сигнал подаётся
только на переход «пусто → появились», иначе он превращается в шум.

**Тревога переработана: теперь она даёт данные для звонка.** Прежде тревога
объявлялась одним нажатием и не несла сведений — оператор оставался с красной
полосой и без единого слова для диспетчера.

| Что добавлено | Зачем |
|---|---|
| Выбор обстоятельств одним нажатием (без сознания в воде / тонет / без сознания на бортике / ребёнок без взрослого / травма / иное) | первое, что спросят в трубке; ответ должен появиться вместе с тревогой |
| Карточка тревоги: адрес крупно, ориентир для въезда, проход внутри | оператор не должен вспоминать адрес в момент, когда счёт на секунды |
| Готовый текст для диспетчера + копирование в буфер | читается вслух сверху вниз в порядке вопросов диспетчера |
| Телефоны служб с пометкой, кому и когда; нажатие копирует номер | 112 и 103 вписаны сразу, внутренние — из настроек объекта |
| Первые действия по обстоятельству | в панике порядок действий забывается |
| Счётчик «прошло ММ:СС» | врачи спрашивают об этом в первую очередь |
| Поле уточнения, попадающее в текст на лету | подробности вспоминаются уже во время разговора |
| Повтор звука каждые 6 с до нажатия «Принял» | один сигнал оператор может прослушать |
| `config/site.json` — сведения об объекте | заготовка создаётся сама; поля помечены `НЕ ЗАПОЛНЕНО` |

**Программа не придумывает адрес.** Пока он не заполнен, при запуске висит
жёлтое предупреждение, а в карточке стоит «АДРЕС НЕ ЗАДАН — назовите его
сами». Выдуманный адрес хуже отсутствующего: по нему уедет скорая.

**Замерено** (8 ядер, собранная программа):

| Что | Результат |
|---|---|
| Запись с людьми, 20 с | люди найдены в 100 % разобранных кадров, до 8 одновременно |
| Четыре фотографии пустого бассейна | 0 ложных срабатываний |
| Один разбор кадра | 38–44 мс |
| Три источника с распознаванием | 14,6 % процессора, 292 МБ |
| Четыре источника с распознаванием, 75 с работы | 19,3 % процессора, память 292 → 296 МБ |

Автотестов стало 23: добавлены проверки распознавания на настоящем кадре из
записи и на фотографии пустого бассейна, поведения при отсутствующей модели,
чтения и записи сведений об объекте, состава текста для звонка и
предупреждения о незаполненном адресе. Сценарий тревоги проверен живым
прогоном: объявление, выбор обстоятельства, карточка с адресом и телефонами.

**Не сделано на этом шаге:** Сигнал 2 автоматически. Модель отвечает только
на вопрос «здесь человек?» и отличить тонущего не может; подавать по ней
тревогу означало бы обманывать оператора. Место подготовлено —
`AnalysisWorker::analysePanel()` и сигнал `drowningSuspected()`, уже
соединённый с обработкой тревоги.

### Шаг 1.15 — Опасные положения тела, усиленная тревога, настройки и журнал

Шаг закрывает всё, что выполнимо **без записей с объекта**. Формулировка цели
изменена сознательно и зафиксирована в интерфейсе и в документации: система
**не ставит диагноз «человек тонет»**, а **не даёт человеку остаться
незамеченным**. Разница не косметическая:

* технически — надёжной модели распознавания утопления не существует;
  настоящее утопление тихое, обучающих записей нет ни у кого, вода мешает
  камере. Обещать диагноз означало бы обманывать заказчика;
* юридически — система, заявленная как «распознаёт утопление», при пропуске
  становится причиной иска; система, привлекающая внимание оператора,
  остаётся вспомогательной, чем и является;
* практически — исход при утоплении решает не распознавание, а то, что
  спасатель взглянул на десятой секунде, а не на девяностой.

**Распознавание опасных положений** (перенесено из стенда
`pool_safety_qt/danger_detection_demo/`, метод не изменён):

```
кадр → YOLOv5n (люди) → RTMPose-m (17 точек) → биомеханика →
     → дорожка человека (15 с) → пять правил → НОРМА / ВНИМАНИЕ / ТРЕВОГА + причины
```

| Решение | Обоснование |
|---|---|
| Между позой и решением — слой измерений, а не вторая нейросеть | ответ «0,87» нечем проверить, нечем объяснить оператору и не на чем обучить: записей утоплений нет |
| Модель позы RTMPose-m (Apache 2.0), не YOLOv8-pose | AGPL-3.0 у Ultralytics означает раскрытие исходников либо покупку лицензии — для гостиницы неприемлемо |
| Окно (6 с) считает движение, история (15 с) — длительности состояний | порог «10 секунд неподвижности» внутри шестисекундного окна недостижим в принципе |
| Отметка «панель смотрит на воду» задаётся оператором | «не видно ног» на бассейне означает воду, а в помещении — стол или лежак; без отметки водные правила молчат |
| Признак ребёнка **лишён права поднимать тревогу** до калибровки | единственный из пяти, не проверенный ни на одном настоящем ребёнке |
| Каждый вердикт несёт список причин обычными словами | оператор снимает ложную тревогу за секунду, а пороги настраиваются осмысленно |

**Тревога переработана так, чтобы её нельзя было не заметить** (требование
заказчика: «должна реально привлечь внимание оператора»):

| Что | Прежде | Теперь |
|---|---|---|
| Звук | один сигнал раз в 6 с | **непрерывная сирена** до нажатия «ПРИНЯЛ» |
| Если реакции нет | ничего | через 20 с сирена резче и громче, окно снова наверх |
| Окно | ничего | разворачивается и выводится поверх остальных |
| Панель задач | ничего | значок мигает, пока окно не активно |
| Панель и карточка | статичная рамка | мигают, пока тревога не принята |
| На кадре | рамки | **крупная подпись с уровнем и причиной**, читаемая издалека |

**Окно настроек** (`Ctrl+,`) — четыре раздела: объект (адрес, заезд, проход,
ответственный), телефоны (список в порядке звонков, добавление и
перестановка), тревога и звук (громкость, повтор, усиление, поведение окна),
распознавание (темп, пороги правил, отметка водных панелей). Кнопка
«Проверить» показывает готовый текст для диспетчера с текущими настройками.

**Журнал событий** (`Ctrl+L`) и файл `logs/ГГГГ-ММ-ДД.log`. Появился по итогам
проверки: все измерения жили только на экране, и проверяющий, лежавший на полу
в роли пострадавшего, прочитать не мог ничего.

**Найдено и исправлено проверкой на живых людях — четыре ложных срабатывания
и одна тихая поломка:**

1. «Неуверенная походка» у обычных прохожих: дрожание точек скелета
   раздувает виляние у дальних фигур. Правило требует туловище не мельче
   60 точек и путь не короче двух длин тела.
2. «Ребёнок в воде без взрослого» на человеке, сидящем за столом: «не видно
   ног» считалось водой. Введена отметка водных панелей.
3. Одинокий взрослый опознавался ребёнком: вблизи камеры отношение головы к
   туловищу вырастает до 0,43–0,75 против 0,22–0,30 вдалеке. Порог поднят до
   0,50, добавлена полоса правдоподобия, тревога запрещена до калибровки.
4. Дальний взрослый опознавался ребёнком по признаку «ниже остальных»:
   камера не знает расстояния, «ниже» и «дальше» для неё одно и то же.
5. **Настройки молча не читались из файла**: русские ключи сравнивались как
   Latin-1, и ни одно значение не подхватывалось — программа работала на
   значениях по умолчанию, а оператор был уверен, что правки применились.

**Замерено** (8 логических ядер, собранная программа):

| Что | Результат |
|---|---|
| Один разбор кадра (люди + поза + правила) | 100–190 мс |
| Три записи с людьми, 3,5 минуты | 35 % процессора, 409 МБ, память не растёт |
| Ложных срабатываний за тот же прогон | **0** (до исправлений — десятки) |

Автотестов стало **42**. Каждое исправление закреплено отдельной проверкой,
чтобы, поднимая чувствительность, нельзя было молча вернуть ложные
срабатывания.

**Не сделано и почему:** настройка порогов под реальную сцену, калибровка
признака ребёнка, разметка линии воды в кадре. Всё это требует записей с
бассейна, которых пока нет. Перечень необходимого — в конце
`pool_safety_qt/README.md` и в `danger_detection_demo/WORKLOG.md`.

### Шаг 1.16 — Почему правила молчали, замена модели, выключатели, поставка

**Найдена причина главной жалобы «не срабатывает, когда нужно».** Она не в
правилах и не в модели: рвались дорожки людей. Все временные пороги («лежит
10 секунд», «завис в воде 9 секунд») считаются по дорожке; разбор идёт
несколько раз в секунду, за 0,4 с идущий человек смещается на полкорпуса, его
новая рамка почти не перекрывается с прежней — сопоставление заводило нового
человека, накопленное время обнулялось. Внешне всё выглядело исправно: рамки
рисовались, люди считались.

Замерено на записи с идущими людьми (100 разборов, ~6 человек в кадре):

| Сопоставление | Дорожек создано | Живёт в среднем |
|---|---|---|
| пересечение рамок 0,25 — как было | 204 | **1,2 с** |
| предсказание по скорости + порог 0,15 | 71 | 3,5 с |
| то же + близость центров | **22** | **11,3 с** |

Исправлено двухступенчатым сопоставлением с предсказанием положения. В живой
программе сопровождение выросло с 1,2 до **20,5 с**; показатель выведен в
шапку окна, чтобы поломка такого рода больше не была невидимой.

**Заменена модель поиска людей: YOLOX вместо YOLOv5n.** Две причины:

* *лицензия* — YOLOv5n от Ultralytics распространяется под AGPL-3.0, что для
  гостиницы означает раскрытие исходных текстов всей системы либо покупку
  отдельной лицензии. YOLOX и RTMPose — Apache 2.0;
* *точность* — замер на 120 кадрах при одинаковых порогах: YOLOX-s находит
  5,73 человека в среднем при 35 % провалов счёта, YOLOv5n — 5,30 при 56 %.

Кадр теперь вписывается с сохранением пропорций, а не растягивается в квадрат:
растяжение делало фигуру приземистой и мешало модели. Вид модели программа
определяет сама по форме выхода, поэтому файл модели можно подменить без
правки настроек. В настройках выбор: точная (YOLOX-s), быстрая (YOLOX-tiny) и
прежняя; смена применяется перезагрузкой модели, без перезапуска программы.

**Выключатели откликов** (требование заказчика). Главный выключатель гасит все
автоматические отклики; отдельно выключаются реакция на появление людей и
каждое из пяти правил. Выключенное правило не считается вовсе. Пока отклики
выключены, в шапке постоянно горит «⚠ ОТКЛИКИ ВЫКЛЮЧЕНЫ»: система не должна
молча притворяться работающей.

**Убраны мёртвый код и недоделки:** неиспользуемые `setDisplayFpsLimit`,
`skippedFrames`, `sampleCount`, `velocity()`; подсказка «что делать» пущена в
дело — она показывается оператору при внимании и попадает в текст для
диспетчера; порог поиска и модель применяются на лету вместо прежнего
«вступит в силу после перезапуска».

**Поставка и установщик.** `deploy/build_release.ps1` собирает программу,
прогоняет проверки (и отказывается собирать поставку, если хоть одна упала),
раскладывает поставку, проверяет комплектность по списку обязательных файлов и
пакует архив. `deploy/PoolSafety.iss` — описание установщика для Inno Setup 6.
Отдельно выяснилось: **сборка не работает в пути с кириллицей** (`moc` не может
создать свои файлы в папке «ИИ наблюдение»), скрипт это обходит.

**Проверок стало 46**, все зелёные. Нагрузка: одна запись с точной моделью и
разбором поз — 21 % процессора, 435 МБ.

**Что осталось нерешённым:** «распознавать человека в 100 % случаев» —
недостижимо ни этой, ни любой другой моделью; это свойство задачи, а не
недоработка. Достигнуто лучшее, что даёт открытая модель с приемлемой
лицензией, плюс сопровождение, которое закрывает одиночные пропуски. Пороги
правил по-прежнему ждут записей с объекта.

## 4. ЭТАП 3 — Физическое внедрение на объекте

### 4.1. Как должен выглядеть комплекс (архитектура объекта)

```
[Камера 1]──┐
[Камера 2]──┼──PoE-кабели──▶ [PoE-коммутатор] ──Ethernet (изолированный VLAN)──▶ [Рабочий ПК]
[Камера 3]──┤                                                                         │
[Камера 4]──┘                                                                         │
                                                                                       ▼
                                                                     Главная программа (Этап 1 + Этап 2)
                                                                     • приём кадров с 4 камер
                                                                     • алгоритм распознавания
                                                                     • машина состояний тревоги
                                                                     • интерфейс оператора (монитор на посту)
                                                                                       │
                                                                        ┌──────────────┼──────────────┐
                                                                        ▼              ▼              ▼
                                                                  Экран оператора  Журнал/архив   Эскалация
                                                                  (пост у бассейна)  (диск ПК)    (звонки/SMS
                                                                                                   администратору,
                                                                                                   резервный GSM-канал)
```

**Пояснение по частям, которые вы описали как "не знаю как принято":**

- **"Связующее устройство"** — это **PoE-коммутатор** (Power over Ethernet switch). Стандартная практика для IP-камер: один Ethernet-кабель от каждой камеры до коммутатора одновременно передаёт видео и подаёт питание на камеру. Это удобно и безопаснее именно у бассейна — не нужно тянуть к каждой камере отдельную розетку 220В во влажной зоне.
- **Сервер vs локальный ПК** — ваш выбор (локальный ПК) обоснован: ниже задержка (важно для скорости реакции), не зависит от интернета/облака (важно для надёжности вызова экстренных служб — сеть отеля может лечь, а локальная обработка продолжит работать), нет облачных счетов. Обратная сторона: ПК должен быть выделенным, работать постоянно, иметь дискретную видеокарту (GPU) для обработки 4 потоков в реальном времени — точная модель GPU подбирается после того, как в Этапе 2 будет понятна реальная вычислительная нагрузка обученной модели. Также стоит заранее продумать резервный вариант (например, запасной мини-ПК с копией системы) — единственный локальный ПК является точкой отказа, если он выйдет из строя.
- **Сетевая изоляция** — сегмент от камер до рабочего ПК должен быть отдельным VLAN, не пересекающимся с гостевым Wi-Fi гостиницы (требование безопасности из ТЗ, раздел 7.3).
- **Резервный канал связи** — отдельный GSM-модуль/SIM-модем для эскалации (звонки/SMS администратору), не зависящий от основной сети отеля — на случай, если упадёт именно локальная сеть/интернет-канал.
- **ИБП** — на коммутатор и рабочий ПК минимум для сохранения работоспособности при кратковременных перебоях питания.
